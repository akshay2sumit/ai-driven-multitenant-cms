# Event, State Change and Audit Semantics

## Purpose & Authority

This document defines binding rules for events, state changes, auditability, and evidentiary truth. This document constrains schemas, logging, observability, execution flows, and AI behavior. These rules are constitutional and cannot be overridden by implementation or convenience.

## Event Taxonomy

### Canonical Definition of an Event
An Event is an immutable, timestamped fact that records that a specific action or condition has occurred within a governed context. Events are immutable once recorded. Events are contextual to tenant, system, or governance. Events are causally linked to an action or condition. Events are auditable and non-repudiable. Events are facts, not intentions. Events never retroactively change. Events may be correlated, never merged. Event ambiguity triggers STOP.

### Domain Events
Domain Events represent meaningful changes or occurrences within the business/domain model. Domain Events are always tied to a domain concept. Domain Events must reflect a completed fact, not an intent. Domain Events must be auditable.

### System Events
System Events are generated by the platform to record operational or infrastructural facts. System Events are owned by the system. System Events do not imply domain state change unless explicitly defined. System Events must respect governance invariants.

### Governance Events
Governance Events record governance decisions or transitions. Governance Events are immutable and permanent. Governance Events have higher authority than domain or system events. Governance Events are required for audit and traceability.

### Security & Access Events
Security & Access Events record security-relevant actions or outcomes. Security & Access Events are always auditable. Security & Access Events are immutable by definition. Security & Access Events are retained per security governance.

### Audit Events
Audit Events are created specifically to ensure traceability and compliance. Audit Events are immutable. Audit Events are never suppressed. Audit Events cannot be deleted or altered.

## State vs Event Semantics

### Definition of State
State is the current, authoritative condition of a domain or system at a point in time. State represents what is true now. State is mutable over time. State is derived from prior actions and events. State is always contextual to tenant, system, or governance.

### Definition of State Change
A State Change is a transition from one valid state to another. Every state change must be justified by at least one event. Not every event results in a state change. State changes are authoritative; events are evidentiary.

### Relationship between Commands, Events, and State
Commands represent intent or request. Commands may succeed or fail. Commands are not recorded as truth. Events represent the outcome or fact. Events are recorded as immutable truth. Events may or may not cause state change. State is updated only after valid events. State represents current truth. Commands request, events record, state reflects.

### Explicit Anti-Patterns and Forbidden Practices
Treating events as state is forbidden. Mutating state without an event is forbidden. Retroactively changing state by editing events is forbidden. Allowing commands to directly mutate state is forbidden. State cannot change without a corresponding event. State cannot be changed by replaying commands. State transitions must respect governance invariants. Invalid transitions trigger STOP. Partial state transitions are forbidden.

## Audit Semantics & Evidence

### What Must Be Auditable
State Changes must be auditable. Creation, mutation, archival, and deletion must be auditable. Security Decisions must be auditable. Authentication outcomes must be auditable. Authorization denials and grants must be auditable. Governance Actions must be auditable. Phase authorization and closure must be auditable. Rule creation or modification must be auditable. Delegation Changes must be auditable. Granting, revoking, or expiring authority must be auditable. Exceptional Actions must be auditable. Overrides must be auditable. Violations must be auditable. Forced deletions must be auditable. No silent state change is permitted.

### Definition of Audit Evidence
Audit Evidence is the immutable record that substantiates a claim about a past action or decision. Audit Evidence is immutable once recorded. Audit Evidence is time-bound and ordered in time. Audit Evidence is attributable to an actor and authority. Audit Evidence is contextual to tenant, system, or governance.

### Immutability and Retention Rules
Audit evidence is immutable. Audit evidence cannot be deleted or altered. Audit evidence retention overrides tenant preference. Audit evidence is system-owned. Audit evidence is independent of business state.

### Evidence vs Logs
Audit Evidence is not Debug Logs. Logs may be noisy or partial. Audit evidence must be complete and authoritative. Logs assist debugging; audit evidence proves truth.

## Failure, Ordering & Ambiguity Rules

### Partial Failure Handling
Partial state changes are forbidden. Either the state transition completes and is audited, or the action is treated as not having occurred. Compensation must be explicit and auditable. No half-true state is allowed.

### Event Recording Failure Rules
If an event cannot be recorded, the state must not change. State without event evidence is invalid. Retry does not bypass audit guarantees.

### Audit Failure Rules
If audit evidence cannot be persisted, the action must be blocked. Best-effort auditing is forbidden. No audit means no action.

### Event Ordering Semantics
Events must be orderable by causal relationship. Total global ordering is not required. Conflicting order interpretation triggers STOP. State derivation must respect event causality. Out-of-order event arrival must not corrupt state. State reflects a consistent cut of events.

### Concurrent Action Handling
Concurrent actions must not produce contradictory state. Conflicts must be detected and resolved deterministically. Silent last-write-wins is forbidden.

### Ambiguity Handling Rules
Ambiguity arises when it is unclear whether an action occurred, events conflict, authority attribution is unclear, or timing creates uncertainty. Ambiguity triggers STOP. System must default to safety and non-action. Ambiguity resolution requires governance-defined rules.

## Global STOP Conditions

Immediate STOP is required if any state change occurs without an event, if any event occurs without audit evidence, if any partial or indeterminate outcomes occur, if any conflicting or unordered events occur, or if any ambiguous attribution or authority exists.
