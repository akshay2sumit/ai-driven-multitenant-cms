📐 PHASE 32 — STEP 1
Request Lifecycle & Classification (DESIGN)
🔒 CORE REQUEST PRINCIPLE (LOCKED)

Every request is either a Query or a Command — never both.

Query = read-only

Command = state-changing

Is rule ka koi exception nahi.

🧱 REQUEST DEFINITION (AUTHORITATIVE)
Request

A single, intentional interaction initiated by an actor (human/system/service) that asks the system to either:

Read state (Query), or

Change state (Command)

A request is:

Context-bound (Phase 28)

Identity-bound (Phase 30)

Authorization-checked (Phase 29)

Time-bound (Phase 31)

🟦 QUERY (READ SEMANTICS)
Definition

A request that:

Observes state

Produces output

Does not change system state

Rules

Must be side-effect free

Must not mutate data

Must not emit events (except audit logs)

Must be safe to repeat

Examples (conceptual):

Fetch content

List pages

Preview data

🟥 COMMAND (WRITE SEMANTICS)
Definition

A request that:

Intends to change system state

Produces side effects

Rules

May mutate state

May emit events

Must be authorized

Must be auditable

Examples (conceptual):

Create page

Publish content

Change settings

🔁 REQUEST LIFECYCLE (SEMANTIC)

Every request conceptually passes through:

Receive → Classify → Authenticate → Authorize → Execute → Audit


If any step fails → DENY & STOP.

🔐 FAIL-CLOSED CLASSIFICATION RULE

If request type is ambiguous → deny

If request tries to behave as both → deny

If classification changes mid-processing → deny

🚫 EXPLICITLY FORBIDDEN REQUEST PATTERNS

❌ Read that mutates state

❌ Write hidden inside read

❌ Auto-write during preview

❌ Command disguised as query

🧾 AUDIT & EVIDENCE (DESIGN)

Every request must emit:

Request type (Query / Command)

Actor

Context

Outcome (allowed/denied)

Side-effect indicator

🧭 PHASE 32 — STEP 2
Command Semantics, Side Effects & Idempotency Rules (DESIGN)
🧠 SIMPLE HINDI SUMMARY (MANDATORY)

Kya karenge:
Define karenge ki command ka behaviour kya hota hai, kaunse side effects allowed hain, aur same command dobara aaye to system kaise behave kare.

Golden rule:

Commands change state deliberately — never accidentally.

Kya bilkul mana hai:
Hidden writes, auto-retries that mutate state, ya “user ne dobara click kiya to kuch bhi ho jaaye”.

🔒 CORE COMMAND PRINCIPLE (LOCKED)

A command represents an explicit intent to change state.

Command ≠ request wrapper

Command ≠ API call

Command ≠ business logic

Command is a declarative intent.

🧱 COMMAND EXECUTION SEMANTICS
1️⃣ Explicit Intent Required

Command MUST clearly declare:

What change is intended

System must never infer intent from:

Context

UI

Past actions

❌ Inferred commands are forbidden.

2️⃣ Authorization is Mandatory

Every command MUST pass:

Authentication (Phase 30/31)

Authorization (Phase 29)

No “safe commands”

No “admin shortcuts”

3️⃣ Side Effect Rules (STRICT)

Allowed side effects:

State mutation

Event emission

Audit logging

Forbidden side effects:

Silent secondary mutations

Cross-context mutations

Hidden cascading writes

Every side effect must be:

Expected

Auditable

Traceable to the command

🔁 IDEMPOTENCY SEMANTICS (VERY IMPORTANT)
Definition

Idempotent command = repeated execution results in the same final state.

Idempotency is a property of command semantics, not of transport.

Command Categories
A) Naturally Idempotent Commands

Setting a value to a specific state
(e.g., “set status = published”)

Rules:

Repeating the command does not change outcome

Must not emit duplicate side effects

B) Non-Idempotent Commands

Commands that create new entities
(e.g., “create page”)

Rules:

System MUST detect replays

Duplicate execution MUST be prevented or rejected

No silent duplication

🔐 FAIL-CLOSED IDEMPOTENCY RULES

If idempotency cannot be determined → deny

If replay detection fails → deny

If command classification changes → deny

No “best effort” idempotency.

🚫 EXPLICITLY FORBIDDEN COMMAND BEHAVIOURS

❌ Command triggering hidden queries that mutate state

❌ Command auto-retrying without replay protection

❌ Command partially succeeding

❌ Command mutating state during validation

🧾 AUDIT & EVIDENCE (DESIGN)

Each command must emit:

Command identity

Actor

Context

Intended change

Actual outcome

Idempotency handling result

🧭 PHASE 32 — STEP 3
Query Semantics, Consistency & Read Guarantees (DESIGN)
🧠 SIMPLE HINDI SUMMARY (MANDATORY)

Kya karenge:
Define karenge query ka behaviour, reads kitni consistent hongi, aur system kya guarantee deta hai jab koi data read karta hai.

Golden rule:

Queries observe reality; they never create it.

Query ka kaam dekhna hai, badalna nahi.

🔒 CORE QUERY PRINCIPLE (LOCKED)

A query must be side-effect free and repeatable.

Query ≠ cache warmer

Query ≠ lazy initializer

Query ≠ auto-fixer

Repeat karo → same input → same output (within defined consistency).

🧱 QUERY SEMANTICS (AUTHORITATIVE)
Definition

A Query is a request that:

Reads system state

Produces a representation of state

Does not mutate state

Query execution:

Does not emit business events

May emit audit logs only

🧭 READ CONSISTENCY MODELS (SEMANTIC, NOT IMPLEMENTATION)
1️⃣ Strongly Consistent Read

Reflects the latest committed state

Used when correctness > latency

Rules:

No stale data allowed

If freshness cannot be guaranteed → deny or retry

2️⃣ Read-Committed (Bounded Freshness)

Reflects a recent, committed snapshot

Small, acceptable staleness allowed

Rules:

Staleness must be bounded conceptually

Snapshot must be internally consistent

3️⃣ Eventual Observation

Data may be stale

Used only for:

Analytics

Non-critical insights

Rules:

MUST be explicitly declared

MUST NOT be used for decision-making commands

🔁 QUERY STABILITY RULES

Same query + same inputs + same context
→ same result (within declared consistency)

If consistency cannot be met:

Query MUST fail explicitly

No silent degradation

🔐 FAIL-CLOSED READ GUARANTEES

Ambiguous consistency → deny

Cross-tenant leakage risk → deny

Context mismatch → deny

Authorization failure → deny

No partial reads.

🚫 EXPLICITLY FORBIDDEN QUERY BEHAVIOURS

❌ Query triggering writes

❌ Query auto-fixing data

❌ Query depending on UI state

❌ Query mutating caches with side effects

❌ Query emitting domain events

🧾 AUDIT & EVIDENCE (DESIGN)

Each query must emit:

Query identity

Actor

Context

Declared consistency level

Outcome (success/denied)

🧭 PHASE 32 — STEP 4
Request Context Binding, Authorization Hooks & Failure Rules (DESIGN)
🧠 SIMPLE HINDI SUMMARY (MANDATORY)

Kya karenge:
Define karenge ki request ko context kaise milta hai, authorization kis jagah hota hai, aur failure aate hi system kaise rukta hai.

Golden rule:

A request that cannot be safely evaluated must not proceed.

🔒 CORE REQUEST BINDING PRINCIPLE (LOCKED)

Every request must be explicitly bound to context, identity, and tenant before execution.

Context = Phase 28

Identity = Phase 30/31

Authorization = Phase 29

No implicit binding allowed.

🧱 REQUEST CONTEXT BINDING (AUTHORITATIVE)

A request MUST be bound to:

Execution Context

Authoring

Runtime/Public

System/Background

Governance

Identity & Trust State

Authenticated identity

Trust level

Tenant

Actor tenant

Target resource tenant

If any binding is missing → DENY.

🔐 AUTHORIZATION HOOK PLACEMENT (DESIGN)

Authorization MUST occur:

After authentication

Before command execution

Before query execution

No late authorization.

Authorization Invocation Rules

Every command → authorization required

Every query → authorization required (even read)

Authorization decision:

Uses Phase 29 semantics

Must be deterministic

Must be auditable

🔁 FAILURE SHORT-CIRCUIT RULES

Failure at ANY stage causes:

STOP → DENY → AUDIT


Stages include:

Context resolution

Authentication

Authorization

Consistency guarantee

Idempotency check

No fallback logic.

🚫 EXPLICITLY FORBIDDEN REQUEST FLOWS

❌ Execute then authorize

❌ Authorize only writes

❌ Skip auth for “safe reads”

❌ Retry after partial mutation

❌ Continue on degraded context

🧾 AUDIT & EVIDENCE (DESIGN)

Every request must emit:

Request ID

Request type (Query / Command)

Context

Identity

Authorization decision

Failure reason (if denied)
